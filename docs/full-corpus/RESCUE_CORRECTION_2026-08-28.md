### 2.3 The four records generated by the previous thread are defective — withdraw them

The branch added 8 records (M003, M006, M007, M008, concise + detailed). All 8 carry the
boilerplate provenance string `"...under the four-basis natural-ecology construction rule"`, which
appears on **no other record in the corpus**. They are mechanically generated. Two independent
defects:

1. **They contradict their own dossiers.** All four families are judged
   `needs-additional-evidence`. M003's dossier says explicitly: *"No executable record should be
   built until the public-source gap is resolved or a different evidence-supported profile is
   deliberately registered."*
2. **Duplicate candidate text across pools.** M003, M006 and M008 each contain candidates whose
   text is byte-identical across different source pools. In M003, `pub1` and `exp1` are the same
   sentence — and that sentence is the one the dossier flags as *"a contingency rule, not a
   competing recommendation under the initial factual state."* This violates construction rule 7
   (action distinctness) and makes the cross-source QCCS comparison degenerate: identical
   candidates cannot be action-distinct.

**No base record has this defect.** It is specific to the mechanical generation pass.

**Why this matters more than four records:** the same generator applied to the remaining ~142
records would yield a corpus that passes schema validation, reports as 212/212 complete, and is
methodologically unsound — which would then be pinned as the partner's production evaluation
corpus. That is exactly the padding failure that construction rule 3 and the do-not-do list forbid.

### 2.4 CI on the branch is red, and was silenced rather than fixed

`validate.yml` was changed on this branch to `workflow_dispatch`-only. The original handoff records
this as suppressing "one failure email per intermediate push." Running the official validator against
branch head `cff41aa` locally shows **16 errors, exit 1** — all of one kind:

```
✗ data/benchmark/m00X-...-natural-*.json: candidate fwN has no provenance sources (collection "benchmark")
```

All 16 are on the 8 machine-generated records. So CI was not noisy; it was correctly reporting that
those records were invalid, and it was turned off instead of heeded.

### 2.5 The duplicate-candidate defect is invisible to CI — guard added

Critically, **none** of those 16 errors concern the duplicate candidate text. The validator had no
action-distinctness check at all, so records whose `pub1` and `exp1` are the same sentence would
have passed CI once provenance sources were filled in. A batch-generated 212-record corpus could
therefore have gone green and been pinned for the partner's production run with degenerate
cross-source comparisons throughout.

This session added that guard to `scripts/validate.mjs`, with a demonstration in
`scripts/validate-selftest.mjs` per repo convention. Verified both ways:

- across all 118 candidate-bearing records in `data/` and `releases/`, the only duplicates are the
  6 machine-generated ones — so the guard produces **no false positives** on the existing corpus;
- reintroducing `m003-...-natural-concise-v1.json` makes the validator fail with
  `candidate exp1 (expert) repeats the action of pub1 (public) verbatim`.

## 4. Completion criterion — restated honestly

The original criterion ("106 families / 212 records") should be replaced with:

> Bioethics Bench Full Corpus v1 is author-complete when every one of the 200 families has a
> recorded, evidence-grounded disposition; every family dispositioned executable has exactly one
> canonical matched concise/detailed pair; no record contradicts its own dossier's eligibility
> judgment; no candidate duplicates another candidate's action in the same record; provenance and
> hashes are truthful; CI is green; and the commit is pinned.

**The executable count is an output of that process, not an input to it.** On current repository
evidence it is 31, reaching 39 after Phase C. If 106 is genuinely right, the ~70 promotions must be
re-derived and recorded family by family — which is real research work, not a transport problem.

## 5. Do not

- Do not treat 106, 212, or 150 as targets to hit.
- Do not batch-generate records from dossier text.
- Do not build a record for a family whose dossier says not to.
- Do not let two candidates in one record share the same action.
- Do not mark anything `reviewed_by_human: true`.
- Do not give the partner a pinned SHA until Phase D completes.
